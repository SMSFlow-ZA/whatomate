# Inbox integration contract

This extension is under development. Approved endpoint configuration, definition APIs, durable execution, atomic result application, ordered macro/rule processing, scoped history, explicit idempotent retry, manual outcome/output review, remaining-work cancellation and chained-input review APIs are implemented. Definition/action editing, intent/history and original-operation retry/remaining-work stop reviews are locally qualified. Manual outcome/output review, remaining-sequence resume and feature-disabled emergency-stop screens and full feature acceptance remain outstanding. Do not treat this checkpoint as an accepted customer release or enable live integrations from it.

## Approval and access

An operator registers exact HTTPS endpoints in trusted `inbox_automation.integration_endpoints` configuration. Workspace administrators choose a registered endpoint key when defining an integration; agents cannot enter a destination, custom headers or executable code. Each endpoint fixes its method (`POST`, `PUT` or `PATCH`) and may declare a provider-supported `Idempotency-Key` or `X-Idempotency-Key` header. A declaration must be backed by the provider's durable idempotency contract. The header does not enable automatic retries.

Set an endpoint's `organization_id` to restrict its visibility and use to that organisation. Leaving it empty explicitly makes the endpoint available across organisations on that instance; use this only for intentionally shared destinations. Previews and administrative responses display the destination origin, not its path, because webhook paths can contain secret tokens. The full URL remains operator-side.

Definitions start disabled. Host `integration_dispatch_enabled` and the workspace integration switch default off and are separate from WhatsApp automatic replies and SMS dispatch. Disabling dispatch holds pending work. A request already in flight may finish; a stop cannot retract an accepted external operation.

Managing definitions requires general-settings write permission. Preparing/executing an action also requires chat write, custom-action write, active membership and access to the exact case/account. Mapping an output to a contact field requires contact read and write permissions. Macro visibility will not grant additional execution rights.

## Configure a definition and workflow action

Under **Settings → Inbox workflows → Integrations**, an administrator can create a definition, choose an approved destination and select bearer-token, `X-API-Key` or no authentication. The editor reports whether a credential is stored; it cannot reveal that value. Leave a stored credential unchanged or explicitly replace it. New definitions save disabled. Definition enablement, the workspace dispatch hold and the operator's host hold are independent controls.

Declare named text, number, boolean or date inputs. Names are unique lowercase identifiers, up to 64 characters, using letters, digits and underscores. Mark required inputs explicitly. Selected outputs map top-level JSON response properties to active case/contact fields. Each property and destination field must be unique. An optional reference property retains a bounded string reference without implicitly changing a field.

Choose **Call an integration** in a macro or rule's action editor, select a definition and map its named inputs. Omit optional inputs by leaving them empty. Use `true`/`false` for boolean literals, a JSON number for numeric literals and `YYYY-MM-DD` for dates, or insert a permitted variable. Switching the definition clears its old mappings; changing action type removes integration-specific parameters. Editing a saved workflow keeps the stored definition unchanged until Save succeeds.

Dry run shows the destination origin/method, permitted known values, fields that may change and any deferred input dependencies. It makes no external request. Disabled definitions and dispatch holds remain visible with their intent. A dependent reply is clearly labelled partial; it is not the final approved message. Check the recipient/account and current eligibility again when reviewing actual execution.

If an input schema changes, refresh definitions in the action editor. Obsolete mapping names are shown with an explicit removal control; they are not silently discarded. Complete any renamed required input, remove only the obsolete mappings and save the repaired workflow. Valid mappings remain intact. Reference-property naming errors appear beside the field with the required lowercase identifier format.

Failed lookups offer Retry. A save error keeps the draft, but an uncertain acknowledgement requires refreshing the list before creating a duplicate definition. Unsaved edits are protected when leaving the editor. Viewer, organisation or permission changes invalidate old lookups and clear private credential drafts. Integration settings do not change WhatsApp automatic-reply or SMS controls.

## Inspect recorded operations

Open **Settings → Inbox workflows → History**, then expand **Integration operations** on a sequenced run. Recorded execution state, result source, submission count, provider status and selected-output disposition are shown separately. An administrator's manual attestation is labelled as such; it is not a provider HTTP receipt. A workflow's stopped or blocked snapshot must not be mistaken for an external failure. An already submitted operation can finish after its parent workflow stops.

Use Refresh to check the recorded operation state. Times use the viewer's displayed timezone; this screen is not a live provider query. A refresh failure retains the prior page with a warning that it may be stale. Newer/Older controls use bounded cursor pages, preserving the current page if a request fails. Empty history is not proof that all work has completed.

Expand **Recovery decisions** to inspect recorded reasons, actors and audit identifiers. Each execution-scoped decision shows its action number when available, with the full operation and run identifiers under Audit identifiers. A workflow-level stop is labelled separately. Authorised operators can inspect an investigation reference through a separate request. Ordinary agents see only their scoped metadata and that a reference exists. General history never loads request bodies, response bodies, credentials or selected result values. It does not submit, retry, resume or reconcile an operation.

## Review an original retry or stop remaining work

An authorised operator can choose **Review retry eligibility** on an unresolved or failed operation. This opens a fresh server review; it does not dispatch the request. Check the operation identifier, exact available intent and original provider idempotency deadline, shown in your timezone. A stopped workflow, changed values or definition, insufficient guarantee, lost access or dispatch hold can prevent retry. An empty or mismatched intent cannot be confirmed. Supply a safe single-line audit reason before explicitly authorising the original-operation retry. Its original request and operation identity remain unchanged; the review does not enable any dispatch switch.

Choose **Review stopping remaining actions** on an active sequence to inspect a separate signed cancellation review. It warns about unresolved and in-flight operations. Confirming stops remaining steps; it does not retract a submitted request, fabricate a failure or remove its receipt. Inspect each operation's result independently afterwards. These controls require general-settings, chat and custom-action write permissions plus current case/account access; the server rechecks eligibility when recording the decision.

If the decision acknowledgement is lost, the review retains its exact private payload and decision UUID in memory, locks changes and protects navigation. **Check recorded decision** reads scoped recovery history; older pages can be checked explicitly. An absent record on one page is not proof that the write failed. **Resubmit identical decision** repeats the same confirmation and UUID, not a newly constructed request. A matching recorded decision confirms the local acknowledgement without repeating writes. Provider submission and output disposition still have their own authoritative states.

A conflict requires inspecting current operation/recovery records. Only after explicit acknowledgement of that review can the local confirmation be discarded and a fresh side-effect-free preview requested. This does not undo any server decision or external operation, automatically create a new decision, extend idempotency retention or bypass current eligibility. Viewer or permission changes clear private drafts and reject late callbacks. No private decision payload is written to browser storage, URLs or logs. If a page is forcibly closed despite its warning, an authorised operator must inspect the durable recovery history before deciding what to do next.

## Review remaining workflow actions

In the inbox macro picker, open **Workflow activity** for the current case, then expand **Integration operations**. This case-scoped page requires chat read and does not require access to general settings. Administrators can also use **Settings → Inbox workflows → History**. In a sequenced run awaiting context review, choose **Review remaining actions**. The current run actor needs chat write and the permissions required by each remaining action. A general-settings administrator with chat write may adopt remaining work under their own current permissions. This does not grant access to operator-only retry, manual investigation or evidence controls. Run recovery metadata is available under the existing chat-read, case/account and authored/initiated-run boundaries.

The signed preview shows the current recipient, account, remaining action numbers, authored reply or template, integration inputs and deferred values. It reviews remaining work rather than claiming that the original trigger conditions were matched again. Completed steps retain their original history. A reserved but ineligible customer reply blocks authorisation; a reply that was never reserved is shown for context and will be skipped. Reviewing cannot create a new send reservation. Steps awaiting a later integration result remain held for another review.

Enter a safe operational reason, then choose **Authorise remaining actions**. The server rechecks current state, rights and dispatch controls. If its acknowledgement is lost, use the same protected decision lookup or identical resubmission described above. A matching `resume_sequence` receipt confirms this review; it does not prove that later provider calls or messages succeeded. History lists include run-level resume decisions, while evidence inspection remains restricted. The scoped recovery-record read APIs remain available when the feature is disabled; a disabled feature does not permit new resume mutations.

## Mappings

Definitions allow up to 32 named inputs of type text, number, boolean or date and up to 16 named output-to-field mappings. Inputs use the same bounded variable syntax and permitted contact/case resolver as message personalisation. Number `0` and boolean `false` remain values; an absent optional input is omitted. Unknown mappings, invalid types, unresolved variables and missing required inputs reject preparation.

Outputs select top-level response properties and validate them against active field definitions in the same organisation. No response body becomes script, a URL to fetch or an unrestricted update command. An optional reference key selects a bounded string reference. Only selected validated results are retained, encrypted. Result application checks current case identity, version, workflow/definition revision and field permissions before writing the entire field batch atomically. Empty outputs cannot silently clear existing values. A newer edit leaves the successful provider receipt held with `output_context_changed`; no second external request is made. Integration activity does not trigger rules.

## Transport and persistence

The client accepts exact HTTPS destinations without user-info, query strings, fragments or nonstandard ports. It rejects redirects, private/loopback/link-local addresses, metadata services, reserved address ranges and mixed DNS results. It dials the validated IP while retaining normal TLS hostname verification. Environment proxy settings cannot override this path.

Calls have a 30-second deadline, a 64 KiB request/response bound and a 16 KiB response-header bound. Responses must be a bounded JSON object with unique property names, or an empty HTTP 204 response. Errors expose categories and status/latency, never raw provider error bodies or credentials. The transport does not transparently replay requests.

Credentials are write-only and encrypted with the instance key. Secure storage fails closed if the key is missing. Request snapshots and selected results are also encrypted and never placed in Redis. Preserve the database and instance key together during recovery.

Each run/action index has one stable execution ID and immutable request digest. Atomic claims permit at most two integration submissions across workers in one instance database. Calls run after the claim transaction has committed, without holding the case lock. Completed work is never submitted again. A lost response or interrupted submission becomes `unknown` with `needs_reconciliation`; a non-success HTTP response is not proof that no external write occurred. Definitions, workflow visibility, actor permissions and case context are rechecked before dispatch.

## Ordered workflow execution

An `integration` action references a definition UUID in `value` and maps its declared inputs using `integration_inputs`. Workflow validation rejects missing definitions, unknown input names and missing required mappings. Integrations do not change the legacy execution path for workflows without integration actions.

An integration workflow advances a durable cursor in authored action order. Each local action commits with its cursor change; integration submission and WhatsApp sends happen outside those database locks. A later step waits for the preceding operation's durable result. Required resolution fields can be populated by a preceding integration, but resolution checks the actual validated values again before committing.

Macro review includes the intended destination origin, method, typed inputs and permitted output labels. Its signed confirmation binds the definition and exact request values. Changed definitions, case context or reviewed replies stop the sequence for a new review. Completed operations keep their identities and are not repeated when later work resumes. A message already submitted stays submitted even when a concurrent edit requires review of subsequent steps.

Rule events wait for an integration sequence before evaluating later rules. Later events for the same case wait too; unrelated cases continue. One automatic reply reservation is retained across all rules for the original event. Delivery receipts and integration result activity do not create new rule triggers. Paused work is excluded before selecting a runnable batch, so held replies and unresolved results cannot occupy the whole batch.

Sequence states distinguish work in progress (`integrating`), a message being submitted (`sequence_sending`), changed context requiring review (`sequence_review`), blocked work (`sequence_blocked`) and uncertain external outcomes (`sequence_unknown`). A worker restart reconciles accepted message receipts without sending again. Unknown integration outcomes remain held; a new context review is not external-outcome reconciliation.

## Inputs and replies that depend on earlier results

A later integration input or personalised reply can use a contact/case field populated by an earlier integration in the same workflow. Use the existing field variable, such as `{{case.field.external_reference}}`; there is no raw response expression language or access to another run's values. Only outputs of earlier, permitted definitions establish a dependency. A step cannot satisfy its own input, and future steps cannot supply earlier inputs.

Preflight marks dependent actions as deferred, including when the field already has an older value or an authored fallback. Integration intent exposes `deferred_inputs` by input name and omits those inputs from its known values. Workflow previews expose `deferred_actions` by zero-based action index. A reply exposes `deferred_variables` and uses an ellipsis for pending values; this is a partial intent, not the final approved text. Independent missing values, invalid constants, unavailable output fields and ordinary send eligibility still fail their checks.

The first known actions can run after review. Before a dependent request or reserved reply, the durable cursor stops with `prior_integration_result_requires_review`. No dependent request is queued, and no exact request or reply fingerprint is authorised while its values are unknown. After the previous result is validly applied, preview the remaining sequence again to inspect the exact typed inputs or rendered reply, recipient and account. Confirming this new review authorises only those known values; later dependencies remain deferred and need their own review. Current permissions, type/length limits, template approval, service window, consent and context are checked again. Invalid returned data cannot bypass the next input's declared type.

Repeated events, workers or restarts retain the same completed operations. Field or template changes invalidate an open confirmation. A deferred rule reply retains the event's single send reservation; it does not permit a later rule to send a second reply. If automatic replies were held when the rule queued, that reply stays skipped rather than becoming enabled through dependency review.

## Explicit idempotent retry

Retries are unavailable by default, including for existing endpoints that declare only an idempotency header. An operator may additionally set `idempotency_retention_seconds` after verifying the provider guarantees durable deduplication of the same operation key and payload for that entire interval. Supported explicit intervals are 60 seconds to 30 days; zero retains the no-retry policy. Never infer a guarantee from the existence of a header or a successful HTTP response.

New executions retain a fixed retry expiry starting conservatively at enqueue, before provider acceptance. The expiry never extends on retry. Work needs at least 35 seconds remaining for the bounded provider call and persistence; it is checked both during review and again before dispatch. Historical executions without this recorded guarantee cannot gain it retrospectively.

Only an administrator with chat write, custom-action write and current case access can request a retry. A fresh signed preview verifies the current workflow, definition, original actor permissions, case digest and exact encrypted request. Recovery never changes the operation ID, request body, execution actor or approved destination. The requester must also be permitted to inspect the inputs and mapped fields. A changed definition, revoked access, expired guarantee or emergency hold blocks the request.

The request records a client-generated recovery operation UUID and a safe reason, retaining prior state, outcome, attempt count, status and timing. Repeating that same decision returns its recorded result; changing its payload conflicts. Do not paste credentials, provider error bodies or secret endpoint paths into reasons. Recovery queues work only and does not enable a dispatch switch. An accepted operation returned by the provider advances the existing sequence, not a new external object. Without a verified retry guarantee, unknown work remains held for outcome reconciliation.

## Manual investigation and output review

Investigate an uncertain external operation at the provider before recording an outcome. An authorised administrator can attest that it succeeded or had no effect, with a safe reason and investigation reference. These are explicitly labelled manual attestations, not fabricated HTTP responses. The recovery ledger retains the prior state, outcome, source, attempt count, status and timing. A manual no-effect decision does not confer a retry guarantee or create another request.

Success can be recorded without mapped values, including when the original definition has changed. Supplied values require the original definition revision, current field access and the same bounded type/credential validation used for provider results. Only declared output/reference properties are accepted. Evidence references and selected values are encrypted. General history reveals only whether evidence exists; retrieving the reference requires current operator and case access. Do not paste raw provider bodies, credentials or secret endpoint paths into references or reasons.

Recording success does not apply fields or resume work. A separate signed output review shows permitted field labels and current/proposed values. It binds the stored result, current case context, definition/schema revision and reviewer. All field writes, the handled marker and workflow cursor commit together, or none do. False and zero are valid values. Archived or inaccessible fields, masked phone values, changed definitions and stale confirmations block application. An operator can instead discard outputs without revealing them; discarding never changes a successful external outcome into a failure.

Review uses the current reviewer's permissions while preserving the original execution actor, operation/request identity and initiating user. After applying or discarding the current step's outputs, any remaining actions require a fresh context review. No reconciliation action sends an external request, enables dispatch, triggers another rule or records a human reply for response-target timing.

Cancellation stops remaining workflow steps. It does not retract an in-flight or accepted operation, erase receipts or resolve uncertainty. Never-submitted pending work is cancelled; a cancelled pending retry retains its unresolved original outcome. An in-flight integration may finish after cancellation, and its execution record remains authoritative. Review or discard its returned outputs separately. A WhatsApp submission with an unknown outcome must be reconciled through the message path before cancelling its sequence. Stopping remaining work remains available when the inbox feature or encryption key is unavailable; it does not enable any feature or dispatch switch.

## Administrative and workflow APIs

- `GET/POST /api/inbox/integrations` and `PUT/DELETE /api/inbox/integrations/{integration_id}` manage definitions. Requests specify `endpoint_key`, not a URL. Updating without a credential preserves the existing encrypted value. Responses expose `has_credential`, never the credential or ciphertext.
- `GET /api/inbox/integration-catalogue` exposes scoped definition metadata/input schemas for the action editor.
- `GET/PUT /api/inbox/integration-settings` read or change the workspace hold without changing unrelated organisation settings.
- Deletion rejects definitions still referenced by workflows or unresolved executions; use disable to stop future dispatch.

- Existing workflow preview/execute interfaces accept the integration action and return safe integration intent in `integrations`, indexed by action position. General run history includes sequence state, action cursor and original initiator; encrypted plans, requests and results stay private.
- `POST /api/inbox/workflow-runs/{run_id}/preview` previews the remaining actions of a blocked/context-review sequence. `POST /api/inbox/workflow-runs/{run_id}/resume` requires that fresh `confirmation` and a nonempty `reason`. Both require current case access. A general-settings administrator may adopt remaining work using their own permissions while preserving the original initiator. Preview does not grant additional execution rights.
- New resume clients should also send a fresh UUID `operation_id`. Its decision record commits atomically with the approved plan/state changes and is returned as `recovery` alongside safe current `run` metadata. With current feature and write access, an identical request by the same authorised actor returns that recorded receipt without advancing the cursor, repeating local actions or submitting again, including after worker restart. Reusing the identifier with another actor, run, confirmation, reason or recovery kind conflicts. New-ID requests reject nil UUIDs, multiline/unsafe audit reasons and known current integration credentials/secret endpoint paths. Calls that omit `operation_id` keep the legacy response shape and require a confirmation matching the currently reviewable state; they do not gain durable receipt replay. If the feature is disabled, inspect scoped recovery history instead of attempting another mutation.
- A client must match the resume receipt's identifier, `resume_sequence` kind and run identifier. A completed or changed run is not a substitute acknowledgement. Keep the exact reviewed request and identifier in private memory after an uncertain response; explicitly inspect bounded run recovery history or repeat only that identical decision. A missing record on one page does not prove that it failed to commit. Clear private state when the viewer or permissions change, and obtain a fresh review before a different decision.
- Resume rejects submitted/unknown external work. It may replace only a never-submitted pending/blocked request after a signed review, preserving its operation ID. A request locked by a dispatcher produces a conflict requiring refresh, rather than waiting while holding parent locks.
- `GET /api/inbox/integration-executions` lists safe execution metadata, with optional `case_id`, `run_id` and `state` filters. `GET /api/inbox/integration-executions/{execution_id}/recoveries` lists recorded recovery decisions. Pages contain at most 50 rows; pass the returned `next_cursor` as `cursor` for the next page. Offset paging is not supported. Current organisation/account/case and run-author visibility apply before pagination. History does not decrypt requests or results.
- `POST /api/inbox/integration-executions/{execution_id}/retry-preview` returns eligibility, a reason, the exact safe intent, fixed expiry and an opaque `confirmation`. `POST /api/inbox/integration-executions/{execution_id}/retry` requires that confirmation, a nonempty safe `reason` and a fresh UUID `operation_id`. HTTP 409 requires review again; HTTP 403/404 means the current user lacks the necessary scope. A replay returns the current execution state, so an already completed operation does not appear newly queued.
- `POST /api/inbox/integration-executions/{execution_id}/recovery-preview` accepts `action`: `confirm_succeeded`, `confirm_not_applied`, `apply_outputs` or `discard_outputs`. Outcome attestations require `evidence_reference`; success may include a typed `result` object containing only declared properties. Field-disposition actions accept neither property. The response includes eligibility, a safe reason, permitted field changes and an opaque `confirmation`. `POST /api/inbox/integration-executions/{execution_id}/recover` adds that confirmation, a safe nonempty `reason` and fresh UUID `operation_id`. Repeating an identical recovery operation returns its recorded decision without repeating writes; a conflicting reuse or stale review returns HTTP 409.
- `GET /api/inbox/integration-executions/{execution_id}/recoveries/{recovery_id}/evidence` returns only the encrypted investigation reference after operator/case authorisation, with phone masking where applicable. It never returns the provider body, credential or encrypted payload.
- `POST /api/inbox/workflow-runs/{run_id}/cancel-preview` returns whether cancellation is eligible and warns about unresolved or in-flight operations. `POST /api/inbox/workflow-runs/{run_id}/cancel` requires the fresh `confirmation`, safe nonempty `reason` and fresh UUID `operation_id`.
- `GET /api/inbox/workflow-runs/{run_id}/recoveries` lists safe recovery metadata with the same bounded cursor paging, including workflow-level stop and resume decisions without an execution. It requires chat read and current organisation/account/case access. Ordinary agents see only their authored/initiated macro runs; broader workflow visibility still requires general-settings write. These records remain inspectable when the feature is disabled if current case access permits it. Read access does not grant recovery writes or evidence decryption. Run/case/account/contact identities must agree; null-run legacy records are included only through a matching scoped execution. A lost acknowledgement should be checked by its exact decision UUID rather than inferred from an unrelated state change.

Manual outcome/output review and feature-disabled emergency-stop screens and full feature acceptance remain outstanding. Restore/rollback must keep integration dispatch and automatic replies off until pending and unknown work has been reconciled. Older binaries do not understand deferred review markers in encrypted plans; do not resume those plans on an older binary. Keep outbound work held and return to a compatible release for review. A cancelled parent run does not prove that all its external operations are resolved; inspect the scoped execution records as well.
