The Inbox is where your team has day-to-day conversations with customers over WhatsApp. It's a shared, real-time view: incoming messages arrive live over WebSocket, agents reply with text, media, buttons, or approved templates, and each conversation carries its own assignment, tags, and private notes.

## The conversation list

The left-hand list is the set of contacts the signed-in user is allowed to see, ordered by `last_message_at` (most recent first, contacts with no messages last). Each row surfaces:

| Field | Meaning |
|---|---|
| **Profile name / phone** | The contact's WhatsApp profile name, falling back to the phone number. Both can be [masked](#phone-masking) org-wide. |
| **Last message preview** | A short preview of the most recent message (`[Image]`, `[Document: …]`, or truncated text). |
| **Unread count** | Number of **incoming** messages that haven't been marked read. |
| **Assigned agent** | The agent the conversation is routed to, if any. |
| **Tags** | The contact's tags. |
| **Service window** | Whether the 24-hour free-form messaging window is open (see below). |

### Search and tag filtering

The list supports server-side search and tag filtering:

- **Search** matches the contact's phone number or profile name (case-insensitive on the profile name).
- **Tag filter** accepts a comma-separated list of tag names and returns contacts that have **any** of them (`?tags=vip,billing`).

These map to the `search` and `tags` query parameters on `GET /api/contacts` — see the [Contacts API](/whatomate/api-reference/contacts).

### Unread counts

A conversation's unread count is the number of incoming messages whose status is not yet `read`. Opening the conversation and calling **mark-as-read** clears it (see [Marking messages as read](#marking-messages-as-read)). When the chatbot auto-handles an exchange, it marks the incoming messages read for you so bot-handled chats don't leave a stale unread badge.

## The 24-hour service window

WhatsApp enforces a **24-hour customer service window**. It opens each time the customer sends you a message and lasts 24 hours from that last inbound message. Whatomate tracks this per contact as `service_window_open` (true when the last inbound message was less than 24 hours ago).

What the window controls:

| Window state | What you can send |
|---|---|
| **Open** (customer messaged within 24h) | Free-form messages — text, media, interactive buttons, reactions. |
| **Closed** (no inbound in 24h) | **Only pre-approved [message templates](/whatomate/features/templates).** Free-form messages will be rejected by Meta. |

<Aside type="note">
  This is a WhatsApp Platform rule, not a Whatomate limitation. To re-open a conversation after the window closes, send an approved template; once the customer replies, the free-form window opens again.
</Aside>

## Permission-scoped visibility

What a user sees in the inbox depends on their [role's permissions](/whatomate/features/roles-permissions):

- **With `chat:read`** — the user can open conversations. Combined with **`contacts:read`**, they see **every** conversation in the organization.
- **Without `contacts:read`** — visibility is narrowed to conversations the user *owns*: contacts **assigned to them** (`assigned_user_id`), plus contacts with an **active agent transfer** to them. This scoping is applied uniformly to listing, reading, messaging, reactions, and notes — an agent cannot read or reply to a conversation they don't own.

Assignment is controlled separately:

- **`chat.assign:write`** and **`contacts:write`** let a user assign or reassign conversations to agents.

<Aside type="tip">
  The default **agent** role typically has `chat:read` / `chat:write` but not `contacts:read`, so agents see only their own conversations. Managers and admins have `contacts:read` and see the whole inbox.
</Aside>

## Sending messages

All outbound sends target a contact and resolve a WhatsApp account (the one specified on the request, else the contact's account, else the org's default outgoing account).

### Text

Send a plain text message. Supports replying to an earlier message for threaded context.

```json
POST /api/contacts/{id}/messages
{
  "type": "text",
  "content": { "body": "Hi Sarah, how can we help?" },
  "reply_to_message_id": "…optional…"
}
```

### Media

Images, video, audio, and documents are sent as `multipart/form-data` with the file, a `type` (`image` / `video` / `audio` / `document`), an optional `caption`, and an optional `whatsapp_account` override.

```
POST /api/messages/media   (multipart/form-data)
file=<binary>  type=image  caption="Your receipt"  contact_id=<uuid>
```

### Interactive messages

The chat send endpoint also sends interactive messages via the `interactive` field:

| Interactive type | What it sends |
|---|---|
| **button** | Up to a few tappable quick-reply buttons under a body text. |
| **list** | A list-style picker of options. |
| **cta_url** | A single call-to-action button that opens a URL. |
| **voice_call** | A WhatsApp [Business Calling](/whatomate/features/calling) button that lets the customer call you. Requires the account to have Business Calling enabled. |
| **flow** | Launches a [WhatsApp Flow](/whatomate/features/whatsapp-flows) form. The `flow_id` must belong to your organization. |

### Templates

When the service window is closed — or for any structured, pre-approved outreach — send an approved [template](/whatomate/features/templates) via `POST /api/messages/template`. You supply the template name or ID plus its body/header/button parameters. The send is rejected if the template isn't `APPROVED`, if required parameters are missing, or if the contact has opted out of marketing and the template is a `MARKETING` template. See the [Messages API](/whatomate/api-reference/messages) for the full parameter list.

### Reactions

React to any message with an emoji. Each user can have **one** reaction per message; sending an empty emoji removes your reaction.

```json
POST /api/contacts/{id}/messages/{message_id}/reaction
{ "emoji": "👍" }
```

### Marking messages as read

Opening a conversation should mark its incoming messages read to clear the unread badge:

```
POST /api/contacts/{id}/mark-read
```

This flips the contact's incoming messages to `read`. If the sending account has **auto read receipts** enabled, Whatomate also sends read receipts (the blue ticks) back to the customer over the WhatsApp API.

<Aside type="tip">
  Canned responses speed up repetitive replies — type `/shortcut` in the chat input to insert a pre-written message. See [Canned Responses](/whatomate/features/canned-responses).
</Aside>

## Private conversation notes

Notes are **internal annotations** on a conversation. They are stored against the contact, visible to your team in the chat view, and **never sent to the customer**.

- Any user with **`chat:read`** can view notes; **`chat:write`** is required to create them.
- A note records its author and timestamps, and displays the author's name.
- **Only the note's author can edit or delete their own note.**
- Note changes broadcast in real time over WebSocket, so teammates viewing the same conversation see them appear live.

Endpoints (see the route table): `GET` / `POST /api/contacts/{id}/notes`, and `PUT` / `DELETE /api/contacts/{id}/notes/{note_id}`.

<Aside type="note">
  Notes are the right place for internal context ("customer is escalated, waiting on refund approval"). Anything the customer should see must be sent as a message.
</Aside>

## Contact management

Each conversation is backed by a contact record you can manage from the inbox.

### Assignment

Assign a conversation to an agent to make ownership explicit and — for agents without `contacts:read` — grant them access to it. Assignment requires **`contacts:write`**.

```json
PUT /api/contacts/{id}/assign
{ "user_id": "…agent uuid…" }   // null to unassign
```

The assignee must be a user in the same organization. Unassign by sending `null`.

### Tags

Tags are organization-scoped, colour-coded labels. Manage the tag catalog under **`tags:read` / `tags:write` / `tags:delete`**; valid colours are `blue`, `red`, `green`, `yellow`, `purple`, `gray`. Apply tags to a contact (requires **`contacts:write`**):

```json
PUT /api/contacts/{id}/tags
{ "tags": ["vip", "billing"] }
```

Renaming or deleting a tag in the catalog propagates the change to every contact that carries it. Filter the inbox by tag as described in [Search and tag filtering](#search-and-tag-filtering).

### Contact fields

A contact carries a phone number, profile name, WhatsApp account, tags, and a free-form `metadata` object. Creating and editing contacts requires **`contacts:write`**; both are audit-logged. Re-creating a previously deleted contact restores the soft-deleted record rather than erroring.

### Marketing opt-out

Contacts flagged `marketing_opt_out` cannot be sent `MARKETING`-category templates — such sends are rejected. This keeps bulk and promotional messaging compliant with the customer's stated preference.

## Phone masking

When phone masking is enabled for the organization, phone numbers (and profile names that are themselves phone numbers) are masked in list and detail responses. This is an org-level privacy control applied server-side, so agents never see the raw number.

## Real-time updates

The inbox receives live updates for conversations the signed-in user can currently read. Account-specific assignments and active transfers apply to live messages, reactions and delivery updates as well as HTTP reads. Contact-wide notes require contact-level access.

## Track inbox cases

An administrator can enable conversation workflow in **Settings → General**. New cases appear when a customer enters the human inbox. Agents can also select **Start case** in a conversation. Earlier messages remain in the thread.

Use **Open** for active work, **Pending** for an internal wait and **Waiting for customer** when you are expecting a reply. Set a priority when the team needs to see how soon to act. A customer reply reopens a waiting case.

To return to a case at a specific time, select **Snoozed** and enter a date and time. The case returns to **Open** when the deadline is reached or the customer replies. Select **Resolved** when the work is finished. A later reply routed to the human inbox starts another case in the same thread.

Open the contact details panel and expand **Case activity** to see recent status, priority and follow-up changes. If you switch WhatsApp numbers within a contact, the controls show the case for the selected number.


## Work from case queues

When conversation workflow is enabled, Chat starts in **Mine**. Your queue and filters are remembered for your signed-in user and organization; opening another workspace does not reuse them. **Contacts** remains available as secondary navigation. In **Chat → Queues**, use **Mine**, **Unassigned**, **Awaiting first reply** or **Follow-ups** to find the cases you need. Queue counts, incoming-message previews, owner/team, message age and response targets respect your normal access and phone-masking settings. The filters narrow cases by WhatsApp account, team, assignee, status, priority or contact tags. Select a case to open its WhatsApp thread.

Use **Saved views** to name a filter you use regularly. A personal view is available only to you. Team managers with permission can save a view for their team. Each view applies your ordinary case visibility. Personal and team views are grouped separately. Owners can rename and update personal views; authorized team managers can update or remove team views. Controls appear only when permitted. A shared team view always retains its team boundary, even when additional conditions use **Any condition**.

Select cases to resolve them, assign them to an agent or add a contact tag. Review and apply the action, then check the outcome for each case. An item can become unavailable or change before you apply an action. Case assignment applies to the selected WhatsApp account. Tags remain attached to the contact. Each result keeps its contact, inbox and case reference; follow its link to correct an unavailable assignment, stale case or missing detail.


## Use macros and rules

Select **Macros** beside the message composer, choose a macro and review its actions. For replies, check the recipient, sending number and message before confirming. An administrator can build macros and rules in **Settings → Inbox workflows**. Choose the **Rules** or **Macros** tab, search existing items, then select **New rule**, **New macro** or **Edit** to open the editor. Use **Dry run** to preview a rule against a case. **History** has paginated runs with the actor, account, case link, condition results, action results and message reconciliation state. A dry run never sends a message or changes a case. It predicts each action, including assignment eligibility, capacity and required fields. An ineligible reply still shows its intended recipient, inbox and authored text, with a specific reason for the block. Execution rechecks current state.

Rules can run when a case enters the human inbox, when a customer sends a message or when an agent changes case status. New rules start disabled. Rules run in the visible execution order. Add a description to explain their purpose. Cloning a rule creates a disabled copy. Macros can be personal, shared with a team or organization-wide; visibility never grants extra execution permissions. One automatic reply can be queued for a triggering event. Use **Pause automatic replies** to stop queued rule replies. The run history and case activity show whether a reply was queued, sent, held or needs reconciliation. Check delivery evidence before following up on an uncertain send.

Service text requires an open WhatsApp messaging window for the same number. Choose an approved utility template with complete previewable text for other replies and confirm the intended recipients have opted in. The application checks eligibility again at dispatch.

Rules run with their last editor's current permissions. After upgrading an earlier workflow release, review and enable existing rules again so their responsible editor is recorded. Queued replies from an older release are held. Changes to a case, its tags or its field values after actions have been queued also hold the reply for review; the workflow's own actions are included in its saved snapshot. Uncertain submissions require reconciliation and are never automatically resent.

### Additional conditions and routing actions

Choose **All conditions** or **Any condition** for up to 20 additional predicates. Inbox, organization, team and permission boundaries always apply outside this group. Existing quick filters and older field equality matches keep their existing meaning.

- Text equality is case-sensitive; **Contains** matches literal text without regard to case.
- Number and date fields support greater/less comparisons, including inclusive boundaries. Date comparisons use calendar dates without a time of day.
- **Is empty** and **Is not empty** distinguish a cleared value from `0` or `No`. Archived definitions remain usable in existing filters.
- An incoming-message keyword condition examines only the triggering inbound text, never unrelated history. It supports neither wildcards nor regular expressions. Dry runs use explicitly entered synthetic text.
- **Assign team** uses the team's routing strategy and atomic capacity checks. If no eligible agent has room, the case stays visibly unassigned with a reason and routing retries later.
- **Snooze case** requires a duration authored in that action. There is no organization-wide default duration. Rules can match Snoozed cases.

### Keyboard access

The following lifecycle shortcuts work outside text inputs, selectors and open dialogs. They do not send messages.

| Shortcut | Action |
|---|---|
| Ctrl+Alt+Enter | Resolve or reopen |
| Ctrl+Alt+P | Pending |
| Ctrl+Alt+W | Waiting for customer |
| Ctrl+Alt+S | Open the snooze picker |
| Ctrl+Alt+O | Open a case |
| Ctrl+Alt+M | Search macros; review is still required before applying |

## Set response targets and review deadlines

Set first reply, next reply and resolution targets for each WhatsApp account in **Settings → Inbox workflows → Response targets**. Targets begin when work enters the human queue, including handoffs from a bot. Choose elapsed time or a weekly business-hours schedule with a time zone. Waiting for the customer pauses resolution time. The reply deadlines continue during that wait. The next reply target starts with the first unanswered message after an agent reply.

Saving or removing response targets affects **new cases only**. Every existing case retains its assigned policy version, target durations and business calendar. Policy changes do not rewrite completed results. Legacy cases use the policy known at upgrade and are labelled **Legacy snapshot**; this is not evidence of their earlier historical settings.

Pending and Snoozed continue on the configured calendar. Waiting for customer pauses only resolution; first and next reply targets continue. Another unanswered inbound message does not move the original next-reply deadline.

Open deadline details by touch or keyboard to see the due date, time and timezone, alongside remaining working time. The mobile header keeps these secondary details collapsed so the message thread remains prominent.

In **Agent Analytics → Live inbox**, **Live targets** shows breached cases first, followed by the nearest deadline. Risk filtering happens before pagination, and summary counts cover the scoped result set. Refresh and last-updated information make stale data apparent. **Completed response targets** reports first replies, every recorded next-reply cycle and resolutions by date, inbox, team, agent and policy version. Apply filters before exporting: the CSV uses the same applied scope as the displayed results. Completed-target compliance is separate from outstanding work.

## Set workload limits

In team settings, select a WhatsApp account under **Inbox workload** and set a maximum number of Open and Pending cases per agent. A limit of zero leaves the agent unlimited. Cases waiting for a slot stay in the unassigned queue. Automatic routing checks priority and then waiting time in fair retry rounds, so an unavailable team cannot block other teams. A permitted supervisor can assign beyond the limit by entering a reason during review. The case history records the override. The account-specific assignment dialog shows availability and current/maximum workload. The read-only **Agent workload** tab in Live inbox exposes workload without requiring two filters first. Visible workload refreshes every 30 seconds and after changes; lookup and workload failures offer separate retry actions.

Use a named **Capacity preset** to reuse a limit. Preview the exact before/after values before applying it to team members for an inbox. Application copies values into their limits. Editing or removing a preset does not silently change deployed limits. Zero is displayed as **Unlimited** outside editing.

## Record custom fields

Define text, number, date, yes/no and single-select fields in **Settings → Custom fields**. Edit contact fields on the contact page and case fields in the conversation details. Add descriptions to help agents enter consistent values. New keys are generated from the label; an advanced option allows a valid explicit key before creation. Field scope, type, key and choices remain immutable after creation.

Resolving opens **Complete required details** when values are needed. The form identifies each missing case or contact field and your edit permissions. **Save and resolve** commits permitted values and the resolution together; a stale case, changed requirement or invalid value saves neither partially. Values entered in the form are retained when refreshing requirements after a failure. If you cannot edit a required contact detail, use the authorized contact-editor link or ask a supervisor to complete it, then retry. This does not grant contact editing access to ordinary agents. Archiving a field keeps recorded values and existing saved filter matches. Add a field match to a queue filter or workflow condition.
